🐛 但有一个现成的 bug，今天就在偷你的次日起点。
usInterstitial.ts:296-297 把 vEcpm 无条件 push 进 todayImpr，没有 >0 判断： 
if (myEpoch !== epoch || adsOff()) return;
todayImpr.push(vEcpm);          // ← 缺 vEcpm > 0
而 adRevenue.ts:277 是有防护的（if (value <= 0) return;），并注明「test/bidding 请求 AdMob 按设计返回 precision=UNKNOWN 且 value=0」。 所以今天：一条 0 值 PAID 混进 todayImpr → 次日「前 3 次均值」被拉到接近 0 → 第二天从 idx2 起步。 这个 bug 今天是每日一次的影响；新方案里会变成每次曝光都影响路由。 不管上不上新方案都该先修。
⚠️ precision === PUBLISHER_PROVIDED 是自反馈陷阱。 这个值的含义是「这笔钱来自你自己在中介组里手填的 eCPM」—— 它把你自己填的底价原样回传给你。 喂进 mean × 1.3：请求 $120 → 以 PUBLISHER_PROVIDED $120 成交 → mean=120 → ×1.3 → 请求 $160 → … 一路自我强化到 no-fill，全程测的是你自己填的数字，不是市场价。
路由样本只接受 PRECISE / ESTIMATED；UNKNOWN / PUBLISHER_PROVIDED 只记账、不路由。

风险审查

由独立 subagent 实读代码后产出，按严重度排序。

🔴 高

1 ·「循环请求」= 无退避重发，这是全案最危险的一条

机制：高 optimized floor 的单元注定大比例 no-fill。一次 no-fill 往返约 200–800ms。 若「循环」= 在 ERROR 回调里立刻重发，单台设备就是 1.5–5 req/s ≈ 每小时 5,000–18,000 次请求，而同期真实曝光是个位数。 即便收敛到 1s ticker 也是 3,600 次/小时。

现有代码从不这么干：usInterstitial.ts:311-315 的 request() 有三道闸 —— tierActive(idx) 防重复加载、nextAt[idx] 退避时钟、pump() 里的 if (!cacheFull())。 docs/ad-waterfall-US.md §5 已把这条写成红线。新方案在文字上直接推翻了那一段。

政策：Ad serving limits（support.google.com/admob/answer/9493252）明确说限制投放是无效流量保护的执行手段； 无效流量定义（answer/3342054）中「通过自动化方式产生展示或请求」直接命中。

建议：「循环」一律换成现成的退避曲线 —— unit0BackoffBase(3/6…封顶10s)、netBackoffBase(5/10/20/40…封顶60s)、ladderRetryBase(2s/4s)。 任何单元都不能有「没有 nextAt 闸门的请求路径」。

2 · 政策定性变了，而且升级条件已经成立

docs/ad-waterfall-US.md §11 的既定决策写了一句触发条件：「若日后单元上挂载 bidding 广告源，风险显著升高。」 那个条件已经发生了 —— plugins/withAdMobMediation.js:118，Meta 于 2026-07-26 enabled: true， 而 Meta 插页只能作为 bidding 广告源。§11 里的「显著升高」不是未来时，是现在时。

更重要的定性变化：现有瀑布流按填充结果（fill / no-fill）移动窗口，是被动的。 B 方案不是 —— 它按 mean(最近两次实测 eCPM) × 1.3 直接算出一个价格再挑单元发请求。 这正好是行为政策禁止的那句话的字面描述：「通过发布商自建系统，按实时价格信息程序化分配广告请求」 （support.google.com/admob/answer/2753860）。现有实现的措辞辩护余地，在新方案里没有了。

建议：不推翻既定决策，但要明确知道这次是在已知风险上叠加一层定性更重的新风险，而不是同一风险的量变。 Google 认可的等价路径：一个单元 + bidding mediation group（Meta 已就位）+ optimized eCPM floor， 让价格发现发生在 Google 服务端 —— 能拿到本方案约 90% 的收益、零政策敞口，且不用维护 26+ 单元的状态机。

3 · 整个方案里没有一个 iOS 单元；三组单元不存在

见 Tab ① 的缺口清单。补充一个静默失败陷阱：request() 里 if (!UNIT_IDS[idx]) return;（usInterstitial.ts:313） —— 索引越界不报错，会安静地什么都不请求。×1.3 算出 >HK$500 或「低一层」算出 <HK$40 时正好命中 → 该用户整段会话零广告，且没有任何日志。所有索引计算加显式 clamp，越界要 logEvent。

4 · 币种与单位：账户报 HKD，方案里的「$300」没有定义币种

最可能实际发生的 bug。换算链条有两跳：PAID.value = 每次展示的港币 → vEcpm = value × 1000 = 港币 eCPM → 与阶梯底价比较。

owner 举例的「前两次 eCPM，例如 100 和 80」——这两个数从哪来？ 若从 adRevenue.ts 口径取，那是每次展示的港币（约 0.1 / 0.08），×1.3 = 0.117 → 去阶梯里找「高于 0.117 的一层」→ 永远是 idx2。 每一个用户都会被永久锁在最低层，而且没有任何报错。

两个口径现在分居两个文件：adRevenue.ts 全程 per-impression，usInterstitial.ts 用 eCPM，差 1000 倍。

建议：新价值存储用 branded type（type EcpmHkd = number & { __brand:'ecpm_hkd' }）让 TS strict 替你抓这个错； 文档里「$」全改「HK$」；上线前真机打印一次 ad_paid 的 value/ecpm/currency，确认 ecpm 落在 40–500 而不是 0.04–0.5。

5 ·「保底层 = 上一次价值低一层」是单点故障

假设用户稳定在 high=idx6(HK$120) / low=idx3(HK$60)。某次 idx3（底价只是下限）恰好赢到一条 HK$300 的广告 —— 完全正常。 于是下一轮「低一层」= HK$280 → idx14。保底层瞬间从 $60 跳到 $280，几乎必然 no-fill，上层更高也必然 no-fill。 该用户从此两个单元都打不到，只能靠应急路径活着。

现有设计没有这个洞：unit0 是与窗口完全解耦的常驻安全网（usInterstitial.ts:460-462），窗口再飘也影响不到它。 新方案把安全网接到了它要保护的那个信号上。反向也不稳：一次 0 值 PAID 会把保底层压到 idx2 以下 → 越界 → 静默不请求。

建议：保底层用固定低层（idx2 或直接 unit0），不要从价值推导。 一定要动态就加硬上限 min(tier(last)−1, tier(median_lifetime))，并保留 unit0 作为与路由无关的常驻兜底。

6 · 删掉 climb-on-fill，价格发现天花板从 $500 掉到「保底层成交价 × 1.3」

选择性采样偏差（censored sampling）：高层 no-fill 时不产生样本，保底层 fill 时产生样本 → 样本池被保底层主导。 令保底层实际成交 ≈ F，稳态下 high = ceil(1.3F)。代入 F=HK$65：mean≈64 → ×1.3=83 → high=idx5($100)，low=idx3($60)。 系统稳定在「比保底层高一两级」，而不是用户的真实上限。

从 $60 爬到 $500 需要 1.3ⁿ 走 8 步（60→78→101→132→171→222→289→375→488），每步都要求高层恰好填充。 叠加 60s 全局冷却和典型 2–3 条/会话的曝光量，这条路实际走不通。现有的 climb-on-fill 一次会话就能走完。

建议：保留 climb-on-fill 作为上探信号（fill 就上移），价值只用于设定起点 —— 这正是现有 §2「V → 起始窗口」的做法。新方案把「设定起点」的机制误用成了「持续驱动」。

🟡 中

7 · n=1~2 个样本的噪声远大于 1.3 这个信号

插页 eCPM 近似对数正态，log 空间 σ ≈ 0.8–1.2。n=2 时均值标准误 ≈ σ/√2 ≈ 0.6–0.85 log 单位， 对应 95% 置信区间约为点估计的 ×0.2 到 ×5。而 ×1.3 只有 0.26 log 单位 —— 不到半个标准误。 你在用一个远小于噪声的调整量做决策。

更根本的是方差归因：单条插页 eCPM 主要由「地理 + 时段 + 当时哪个广告主在投放」决定， 用户间方差只占总方差的一小部分。你测到的不是用户，是那一秒的拍卖。

建议：阈值从 2 提到 ≥5，并用中位数或截尾均值（方案本来就要记中位数了 —— 就用它）。 或者更诚实：承认单用户价值不可估，改用群体维度（地区 × 天数 × 平台）设静态起点，把个体路由整个砍掉。

8 · 新老标记的时序竞态（详见 Tab ② 2.1）

可行，但不能用现在 installDayIndex() 那条路。 initAds() 在发第一个请求前已有一长串 await（AsyncStorage → bounded 2s → UMP 12s → ATT 30s → initialize 8s）， 再插一次读取毫无压力。但 installDayIndex() 由 initAdFrequency() 填充， App.tsx 与 initAds() 并行 fire-and-forget，输了竞态就返回 0 = 所有人像 day0。

建议：ads.ts 自己读，包在 bounded(...,1500) 里放在 initialize() 之前，不跨模块依赖初始化顺序； 计数器在 OPENED 里 +1；必须做进后台强制落盘，否则被 kill 会丢计数，用户可能永远停在新用户档。

9 · 缓存 2 条 vs 4–5 个并行源 → match rate / show rate 会很难看

day0 用户实际是 onboarding + newbie + 高底价 + 无底价 = 4 个并行源抢 2 个缓存位。

HB_newbie_splash_text_00 结构性最惨：请求率 100%，但在三个地区里展示优先级都排第二， 而排它后面的无底价单元几乎必填充并立刻占满缓存位 → 「请求最多、展示最少」。

更糟的是它挂的是 Google optimized floor。优化底价是 Google 用这个单元的历史表现算出来的， 它会读到「大量请求、大量 no-fill、填充了也很少展示」—— 你在主动毒化它的优化模型。

建议：cacheFull() 闸门对所有源生效（含循环那一路）；缓存位 2→3，或并行源砍到 2； 先去后台看现有 match/show rate 基线 —— 若 show rate 已在 20% 上下，新方案会推到 10% 以下，那是会被人工看的水平。

10 · PAID 的其余三个坑

① PAID 晚于 CLOSED 到达。现有 pump() 在 CLOSED 里就发下一轮请求（usInterstitial.ts:623）， 但下一轮价位依赖刚那条的价值 —— 那个值可能还没到。必须在 PAID 回调里重新规划，而不是只在 CLOSED 里规划。

② 生命周期统计量（max / median / mean / LTV）是终身概念，必须独立持久键， 不能挂 todayImpr（resetDailyState() 清空）或 adRevenue.state（每天 roll）。

③ 币种切换会清空。adRevenue.ts:231-235：账户币种一变，freshDay() 把当天累加器和 carry 全清。 路由存储若复用这段状态，一次币种变更会抹掉所有路由历史，全量用户回落新用户档。

11 · T2 复用美国单元，会推翻代码里已为同一理由做过的一次隔离

ads.ts:80-86 记录得很明确：全球流量原本和美国阶梯的 unit0 共用单元， 导致后台美国阶梯的统计被污染，所以才专门建了独立 ww 单元拆开。T2 复用 = 按比例重新引入这个已修问题。

  1. 归因：混入 T2 后「$120 这层的填充率」同时混着美国和欧洲两种需求，你再也无法据此调底价 —— 而调底价正是这套阶梯存在的唯一理由。
  2. 底价不可分地区：AdMob 手动底价是每单元一个数、对全部流量生效。而阶梯最低层 idx2 = HK$40(≈US$5.1) 已经在多数欧洲市场的插页 eCPM 之上。实际结果：T2 两层恒定 no-fill → 触底 → 8s 冷却空转 → 全靠 _0 兜底。 换句话说 T2 这套路由什么都不会改变，只会平添请求量 —— 这是最实在的反对理由。
  3. 分组本身不成立：组内跨度 ~10 倍，一套共享底价对这个集合没有意义。

EEA 特有：EEA 用户走 UMP（ads.ts:266-273）。未同意的用户只能拿非个性化广告，eCPM 通常掉 50–70%， 对任何有底价单元都是稳定 no-fill。T2 的正确路由维度不是地区，是同意状态 —— 这个信号手里就有，只是没被用于路由。

建议：T2 用独立单元 + 按欧洲实际水平重设底价（美国的 1/3–1/2，且需要低于 HK$40 的层）； 或更省事：T2 先不做阶梯，只做「同意 → 单元 A / 未同意 → 单元 B」这一个二分。

12 · locale 判定对 T2 是系统性偏低，不是随机噪声

deviceRegion.ts 第三级 tz 兜底只覆盖美国（US_TZ_RE），欧洲和澳新没有任何 tz 兜底。

裸 en locale（欧洲、澳洲都常见）→ 前两级拿不到地区 → tz 不匹配美国 → null → 落到 WW。 T2 会系统性漏掉一部分真实 T2 用户，方向固定向下。

反方向：欧洲用户把系统语言设成 en-US（欧洲很常见）→ 判成 US → 拿 HK$120/$300 底价打欧洲需求 → 稳定 no-fill → 直接产生 §1 描述的循环请求。

建议：给 tz 兜底加一组 Europe/* + Australia/* + Pacific/Auckland（一行改动）； 上线前先只加埋点不改路由，用现有 ads_route 跑一周先看清 locale 分布再决定 T2 值不值得做。

13 · newbie 单元与现有 onboarding 单元可能是同一件事

preloadOnboarding() 在路由判定之前无条件发出，maybeShowOnboardingInterstitial() 还绕过 60s 冷却并强制先展示一次。 所以新用户分支辛苦加载的三条广告，最早也要等 60s 之后才可能展示一条。

HB_newbie_splash_text_00 名字里的 text 与现有 onboarding 单元「text/image/rich-media only，无 video」的描述高度吻合。 先确认这两个是不是同一件事 —— 若职能重叠，应该是替换而不是再加一个，并发数从 4 降到 3。

docs/ad-waterfall-US.md §7：C1（show() 挂 catch）、C2（50 分钟过期淘汰）、H1（__cleanup() 释放原生监听）、 H2（epoch 防跨天脏回调）、M3（clamp 防越界）、M4/M5（IAP 后彻底停机）。 并行源从 3 涨到 5，每一条的泄漏面积同比放大。特别是 H1 那套 subs[] + 「PAID 故意不进 subs」的处理非常微妙，重写最容易漏。

16 ·「≤2 次展示的老用户」其实是你最低价值的人群

day0-2 是新用户很合理（安装类广告主对新装机出价确实高）。但「装了很久、总共只看过 ≤2 条广告」的用户 是几乎不用这个 app 的人 —— 留存最差的一档，不是高价值档。把 HK$300 探针指向他们，得到的会是纯 no-fill。

建议：两类分开 —— day0-2 走新用户探针；「老用户但曝光少」直接走 B 的冷启动路径（_0 兜底 + 一层低价）。

17 · 兜底触发比现有的更激进一点

方案说「缓存一条都没有则必发 _0」，现有是「缓存空且持续 ≥3s」（UNIT0_EMPTY_DELAY_MS）。 差别：每次 CLOSED 后缓存都会瞬时为空，去掉 3s 意味着每条广告关闭都额外触发一次 _0 请求。保留那 3 秒。

如果只改三件事
  1. 把每一处「循环请求」换成带 nextAt[] 闸门的退避。 这是唯一一条能让 AdMob 账号被限制投放的改动，也最容易改 —— 三条退避曲线就在 usInterstitial.ts:169-180。 没有这一条，其余讨论都不重要。
  2. 先把币种和单位口径钉死，再写路由代码。账户报 HKD，PAID.value 是每次展示的港币，阶梯底价是港币 eCPM，中间差 ×1000。 搞错这一跳，全量用户静默锁死在 idx2 且不报错。顺手修 usInterstitial.ts:297 那个 0 值 PAID 进样本池的 bug —— 它今天就在偷你的次日起点。
  3. T2 别复用美国单元，也别急着做 T2。先给 deviceRegion() 加 Europe/Australia 的 tz 兜底， 用现有埋点跑一周拿到真实分布再决定。现在这个方案对 T2 用户的净效果是「什么都没变，但请求量翻了三倍」。
