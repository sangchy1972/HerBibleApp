## 一、120 条经文是怎么凑出来的

| 来源 | 条数 | 说明 |
| --- | --- | --- |
| dailyverses.net top-100（KJV） | **99** | 4 页 × 25 全部取全、去重核对 |
| 试点批已写、不在 top-100 的 | **5** | 耶利米哀歌 3:23 / 彼前 5:7 / 林后 4:16 / 箴言 4:18 / 出 33:14 |
| dailyverses 主题页补充 | **16** | peace / rest / forgiveness 三个主题页，**偏晚间** |
| **合计** | **120** | 早 60 / 晚 60，32 卷书，无重复 |

### 三件我替你做的决定，你可以推翻

**1. top-100 里排除了 1 条：`1 Corinthians 6:9-10`。**
那是一段恶行清单，单节抽出来做每日灵修，几乎一定会被读成定罪，直接撞 §3 的「不制造罪疚」。所以是 99 条不是 100 条。

**2. 19 条多节区间按已定规则「只取单节」，各取区间内最能独立成立的一节。**
例如 `1 Cor 13:4-5` → `13:4`；`Prov 3:5-6` → `3:5`；`2 Tim 3:16-17` → `3:16`。区间原文我在 `b2_plan.py` 里逐条记了，随时可以改选另一节。

**3. 必须从主题页补 16 条，否则晚间池不够。**
这是 top-100 榜单本身的性质：它严重偏向「盼望 / 力量 / 应许」，晚间需要的「安息 / 交托 / 平安 / 赦免」类严重不足。我从 peace / rest / forgiveness 三个主题页补了 12 条晚间 + 4 条早间，才凑出 60/60。**下批如果还从 top-100 抽，这个结构性缺口会再次出现**，建议把主题页固定为第二来源写进 §3。

## 三、🔴 交付前必须知道的两件事

### 1. modern（NIV）仍然是凭记忆重建的

这批 120 条的 `translations.en.modern` 与 `niv_primary` **依然没有正源**，和试点批同一个问题：§4b 只给了 traditional 的语料 URL。NIV 我比其他译本有把握得多，但 120 条里一定有措辞出入，而且从记忆复制受版权译本进产品，和从授权来源使用是两回事。

**这一栏必须在上线前用持牌来源逐条替换。** traditional（KJV）那一栏没有这个问题——120 条全部逐字取自语料库，并已独立复核。

### 2. ⚠️ 11 条诗篇埋着七语言的编号地雷

我选了 16 条诗篇，其中 **11 条的希伯来原文有题记（superscription）**：

`诗 4:8 / 20:4 / 23:1 / 32:5 / 42:11 / 46:10 / 56:3 / 73:26 / 121:7 / 133:1 / 143:8`

英文这批没问题——我实测确认了这个语料库的 en 版**不把题记算作第 1 节**（诗 23:1 是「The Lord is my shepherd」，诗 46:1 是「God is our refuge」），与 KJV 编号一致。

但 **Louis Segond 1910 等译本会把题记算成第 1 节，导致整篇位移**。做七语言时这 11 条必须逐语言重跑 §4b 四步核对，核不齐的按规则换选。诗 46:10 尤其危险（KJV 46:10 很可能 = LSG 46:11），而它是「你们要休息，要知道我是神」这句名句，换掉可惜——建议优先单独核。

风险名单已写进 `b2_kjv.py` 的 `PSALM_SUPERSCRIPTION_RISK`，`b2_verify.py` 每次跑都会提醒。

## 四、还有一处语料库数据问题（新发现）

语料库的 en 版对 YHWH 一律用 **`Lord`（仅首字母大写）**，不是 KJV 传统的 **`LORD`（全大写小型大写）**。我实测确认这不是取用环节的规范化，语料库里存的就是 `Lord`，所以我逐字照抄了——**app 内每日经文与整章正文会一致，这是对的**。

但如果你希望 app 显示传统的 `LORD` 排版，那要在语料库侧统一改，不能在内容侧改，否则每日经文和整章正文会不一样。这是工程侧的决定。
